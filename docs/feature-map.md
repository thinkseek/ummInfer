## 0. 固定维护与派活协议

1. **开工前必读（派活前置）**：后续任何执行 Agent 接手任务开工前，必须先读取本文件中与改动范围相关的功能行、已知缺口（`未验证` / `部分覆盖` / 第 9 节计划中边界）以及协议与硬件约束（含 [docs/architecture.md](architecture.md)、[docs/model-support.md](model-support.md)、[docs/roadmap.md](roadmap.md)），不得在未核对既有契约的情况下盲改或重复实现。
2. **主对话输入职责**：主对话负责向执行或维护 Agent 提供明确的新需求与范围边界、用户已拍板的决定（含优先级与取舍），以及真实环境的部署证据（目标环境、部署版本/commit、在线验证结果）；Agent 不得自行臆造用户决定或线上部署状态。
3. **执行 Agent 完成回写**：执行 Agent 完成任务后，必须同步回写本文件中受影响的功能行（入口、核心实现、协议/契约、验证、状态），更新基线说明（若锚点随新提交迁移），并附上对应 commit 与测试/校验命令证据；如改动导致 AOCI 漂移，须按官方流程刷新 AOCI 索引与基线，并运行 `python3 -I tools/check_feature_map.py`、`aoci check`、`aoci verify` 及文档链接检查。
4. **固定维护 Agent 按需复核**：固定维护 Agent 仅在明确事件触发时（如 `main` 合入、阶段验收、发现锚点/状态漂移或主对话显式派活）按需复核并收口漂移；**禁止空跑定时任务或无事件轮询**。
5. **交付与验证状态严格分离（`merged` / `deployed` / `NOT_RUN`）**：
   - `merged`：代码与离线契约/单元测试已合入 `main`（附 commit 与离线检查输出），**不代表已上线，也不代表真实模型/GPU 已验**。
   - `deployed`：仅当具备主对话或运维提供的真实部署环境、运行版本/commit 与在线探活/业务验证证据时方可声明，缺证据不得标记已部署。
   - `NOT_RUN`：当前环境因无 GPU、无真实权重或未接入目标集群而未执行的验证项（如 GPU 核、真实大模型推理、真实视频后端、NVIDIA Hopper (SM90) 常驻服务），必须显式保留 `NOT_RUN`，严禁用 mock/离线测试桩冒充真模型或部署验收。

- `已实现（契约/单测已验）`：仓库内有离线契约测试、单元测试或 mock/TinyCTC 断言该行为；仅代表离线契约已验（`merged` 维度），**不代表 `deployed` 或真实大模型/GPU 验证**。
